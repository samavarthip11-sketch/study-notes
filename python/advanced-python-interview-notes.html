Chapter 1

🏗️ Object-Oriented Programming (OOP)

The foundation of writing clean, scalable, production-level Python code.

❓ What is OOP and Why Do We Use It?

OOP is a way of organizing code by bundling related data (variables) and behavior (functions) into a single unit called a class.

  • Reusability — Write a class once and reuse it anywhere in the project. No need to copy-paste functions every time.
  • Scalability — You can add new features to a class without touching or breaking any existing code.
  • Readability — Code organized into classes is much easier for your team (and future-you) to understand and maintain.
  • Grouping — Instead of having hundreds of loose, unrelated functions, OOP groups them by purpose into neat logical units.

📦 What is a Class?

A class is a blueprint or template that defines what attributes (data) and methods (behavior) an object will have.

  • You create a class using the class keyword followed by a name (e.g., class MyClass:).
  • Everything inside a class must be indented — Python uses indentation to group code within the class.
  • A class can contain attributes (variables that store data) and methods (functions that define behavior).
  • Think of it like a cookie cutter — the class is the cutter shape, and each object you create from it is a unique cookie.
class MyClass:
    var_one = "hello"      # class-level attribute (shared)
    var_two = 42

    def method_one(self):
        print("Method one called")

    def method_two(self):
        print("Method two called")

🔧 What is a Constructor? (__init__)

A constructor is a special method called __init__ that runs automatically when a new object is created. Its job is to initialize the object's own data.

  • Auto-called — You don't call __init__ manually. Python calls it automatically the moment you write Person("Alice", 30).
  • Accepts arguments — You pass values when creating the object, and __init__ receives them and stores them on the object.
  • Uses self. — You use self.name = name to attach data to the specific object being created.
  • Why needed? — Without a constructor, every object of the same class would share the exact same default values, which is rarely useful.
class Person:
    def __init__(self, name: str, age: int):
        self.name = name   # stored on THIS object only
        self.age  = age

    def introduce(self):
        print(f"I am {self.name}, {self.age} years old.")

alice = Person("Alice", 30)
alice.introduce()  # → I am Alice, 30 years old.

🔗 What is self?

self is a reference to the current object — the specific instance that the method is being called on.

  • Always first parameter — Every method inside a class must have self as its first parameter, otherwise Python raises a TypeError.
  • Auto-passed — When you call alice.introduce(), Python automatically passes alice as self. You don't type it yourself.
  • Accesses object data — Through self you can read and write the instance's own attributes like self.name, self.age.
  • Convention — The name self is just a strong convention. Technically you could name it anything, but never do — always use self.

📊 Class Variables vs. Instance Variables

Class variables are shared by all objects. Instance variables are unique to each individual object.

  • Class variable — Defined directly in the class body (not inside any method). All objects share the same value. If you change it, every object sees the new value.
  • Instance variable — Defined inside __init__ using self.attribute = value. Unique per object — changing one object's variable does not affect others.
  • Accessing class variable — You can access it via ClassName.var or instance.var (read-only from instance).
  • Common use — Class variables are great for counters, shared configs, or default settings. Instance variables hold unique object-specific data like a person's name or age.
class Counter:
    total = 0          # CLASS variable — shared by ALL instances

    def __init__(self):
        self.count = 0  # INSTANCE variable — unique per object

    def increment(self):
        self.count += 1
        Counter.total += 1

Instance variableInside __init__ with self.❌ No — each object only

🔐 Encapsulation & Access Modifiers

Encapsulation means hiding internal details of an object and only exposing what is necessary through controlled methods.

  • Public (attribute) — No underscore. Anyone can read or change it freely. This is the default in Python.
  • Protected (_attribute) — One underscore. A warning to developers: "this is internal, please don't touch it from outside the class." But it's still technically accessible.
  • Private (__attribute) — Two underscores. Python name-mangles it to _ClassName__attribute, so it cannot be accessed directly from outside the class. Accessing it raises AttributeError.
  • Why it matters — Public variables can be accidentally changed by anyone, potentially breaking your logic. Private variables give the strongest protection against accidental modification.
class Vault:
    def __init__(self, secret):
        self.public_data    = "anyone can read this"
        self._protected_data = "be careful — internal use"
        self.__private_data  = secret   # name-mangled

    def reveal(self):
        print(self.__private_data)  # ✅ OK inside the class

v = Vault("top secret")
print(v.public_data)        # ✅ fine
print(v._protected_data)    # ⚠️ works but discouraged
# print(v.__private_data) → ❌ AttributeError

⚙️ Types of Methods: Instance, Class, and Static

Python has three types of methods — each is used for a different purpose depending on whether you need access to the object, the class, or neither.

  • Instance Method (default) — Takes self as the first parameter. Can read and modify both instance and class variables. Used for object-specific behavior. Most methods you write will be instance methods.
  • Class Method (@classmethod) — Takes cls as the first parameter. Operates on the class itself, not on any specific object. Used for updating shared class variables or providing alternative constructors like from_json() or from_csv().
  • Static Method (@staticmethod) — Takes no automatic first argument. It's just a regular utility function that logically belongs inside the class but doesn't need any class or instance data. Example: a helper to validate a file extension.
class Example:
    my_variable = 100

    def instance_method(self):      # needs a specific object
        print(self.my_variable)

    @classmethod
    def class_method(cls, new_val):  # works on the class itself
        cls.my_variable = new_val

    @staticmethod
    def utility():                  # no self or cls needed
        print("General helper function")

✨ Dunder (Magic) Methods

Dunder methods are special methods with double underscores on both sides (like __init__). Python calls them automatically in certain situations.

  • Why "dunder"? — The name comes from "Double UNDERscore". They are also called magic methods because Python invokes them magically without you calling them explicitly.
  • __init__ — The constructor. Runs automatically when you create a new object.
  • __str__ — Controls what gets printed when you call print(obj). Without it, you'd see something unhelpful like <__main__.MyClass object at 0x...>.
  • __repr__ — The developer-facing representation shown in the interactive shell. Should be unambiguous and ideally show how to recreate the object.
class MyClass:
    def __init__(self, name):
        self.name = name

    def __str__(self):                  # called by print()
        return f"MyClass → {self.name}"

obj = MyClass("Demo")
print(obj)  # → MyClass → Demo

🪄 Decorators

Adding extra behavior to functions without changing their original code.

❓ What is a Decorator?

A decorator is a function that wraps another function to add extra behavior before and/or after it runs — without modifying the original function's code.

  • Takes a function as input — The decorator receives the original function as an argument (commonly called func).
  • Returns a new function — It returns a wrapper function that includes the original function call plus your added logic.
  • Applied with @ — Writing @my_decorator above a function is shorthand for fetch_data = my_decorator(fetch_data).
  • Non-intrusive — The original function never knows a decorator is wrapping it. Its code stays clean and unchanged.
  • Used everywhere — Airflow uses @task, FastAPI uses @app.get(), pytest uses @pytest.mark.parametrize. Knowing how they work makes you stand out in interviews.

🧱 How to Build a Decorator — The Structure

Every decorator follows the same 3-part pattern: outer function → inner wrapper → return wrapper.

  • Outer function accepts func (the function being decorated) as its only argument.
  • Inner wrapper function contains your pre-logic, calls the original function (func(*args, **kwargs)), then your post-logic.
  • Return wrapper at the end of the outer function — this is what replaces the original function.
  • Use *args, **kwargs in the wrapper so it can accept any combination of arguments the original function expects.
def my_decorator(func):
    def wrapper(*args, **kwargs):
        print("⏳ Before the function runs")     # pre-logic
        result = func(*args, **kwargs)            # call original
        print("✅ After the function runs")      # post-logic
        return result
    return wrapper

@my_decorator
def fetch_data(url: str):
    return f"Fetching from {url}"

fetch_data("https://api.example.com")
# ⏳ Before the function runs
# ✅ After the function runs

🌍 Real-World Example: Auto-Save DataFrame as Parquet

A classic data engineering use case — automatically save any function's DataFrame output to Parquet, without touching the function itself.

  • Problem — You have many functions that return DataFrames. You want all of them to automatically save to Parquet, but you don't want to copy-paste the save logic into each one.
  • Solution — Write a pandas_to_parquet decorator once, and apply it to any function with @pandas_to_parquet.
  • The decorator calls the original function, receives the DataFrame it returns, then automatically writes it to a Parquet file.
  • Result — Clean, reusable, and the core function stays focused only on loading data — not saving it.
def pandas_to_parquet(func):
    def wrapper(*args, **kwargs):
        df = func(*args, **kwargs)         # original func returns DataFrame
        output = kwargs.get("output_path", "temp.parquet")
        df.to_parquet(output)
        print(f"✅ Saved to {output}")
        return df
    return wrapper

@pandas_to_parquet
def load_csv(file_path: str, output_path: str = "out.parquet"):
    import pandas as pd
    return pd.read_csv(file_path)

🧬 Inheritance

Reusing and extending existing classes without rewriting code.

❓ What is Inheritance?

Inheritance allows a child class to automatically receive all the attributes and methods of a parent class, so you never have to rewrite them.

  • Avoid duplication — Instead of writing the same code in two classes, put it in the parent and let children inherit it for free.
  • Syntax — class Employee(Company): — the parent class goes inside the parentheses.
  • Always call parent constructor — Inside the child's __init__, explicitly call ParentClass.__init__(self, ...) so the parent's attributes are initialized properly.
  • Child can override — A child can define a method with the same name as the parent to replace (override) the parent's behavior.
  • Four types in Python — Single-level, Multiple (parallel), Multi-level (chain), and Multiple-base (two parents).

1️⃣ Single-Level Inheritance

One child inherits directly from one parent. The simplest and most common form.

  • Structure — Parent → Child. The child gets everything the parent has.
  • Call parent constructor — Use Company.__init__(self, company_name) inside the child's __init__ to set up the parent's attributes.
  • Call parent method — Use Company.info(self) inside the child's method to run the parent's version first, then add the child's output.
  • Use case — Employee inheriting from Company — an employee needs all company info plus their own employee-specific details.
class Company:
    def __init__(self, company_name: str):
        self.company_name = company_name
    def info(self):
        print(f"Company: {self.company_name}")

class Employee(Company):
    def __init__(self, emp_name, co_name):
        Company.__init__(self, co_name)   # always call parent first!
        self.employee_name = emp_name
    def info(self):
        Company.info(self)                # parent output first
        print(f"Employee: {self.employee_name}")

🌿 Multiple (Parallel) Inheritance — Many Children, One Parent

Several independent child classes each inherit from the same single parent class.

  • Structure — Parent → Child1, Child2, Child3 (children are siblings, not a chain).
  • Each child is independent — Employee and Contractor both inherit from Company, but they don't inherit from each other.
  • Shared base — All children get the same parent attributes (like company_name), but each has its own unique data and methods.
  • Use case — Different types of staff (employees, contractors, managers) all working at the same company.
class Contractor(Company):
    def __init__(self, contractor_name, company_name):
        Company.__init__(self, company_name)
        self.contractor_name = contractor_name
    def info(self):
        Company.info(self)
        print(f"Contractor: {self.contractor_name}")

⛓️ Multi-Level Inheritance — A Chain

A chain of inheritance: Grandparent → Parent → Child. Each level adds more specialization.

  • Structure — Like a family tree going down: Company → Manager → Employee.
  • Method Resolution Order (MRO) — Python looks for a method in the current class first, then goes up the chain level by level until it finds it.
  • Cascading calls — When Employee.info() calls Manager.info(), which itself calls Company.info() — the full chain fires in order.
  • Use case — Building detailed hierarchies where each level adds more specific information on top of the previous level.
class Manager(Company):
    def __init__(self, mgr_name, co_name):
        Company.__init__(self, co_name)
        self.manager_name = mgr_name

class Employee(Manager):    # Employee → Manager → Company
    def __init__(self, emp, mgr, co):
        Manager.__init__(self, mgr, co)
        self.employee_name = emp
    def info(self):
        Manager.info(self)           # triggers whole chain upward
        print(f"Employee: {self.employee_name}")
# Output: Company → Manager → Employee (in order)

⚡ Multiple-Base Inheritance — Two Parents, One Child

A single child inherits from two completely separate parent classes at the same time, combining functionality from both.

  • Syntax — class Employee(Company, ClientCompany): — list both parents in parentheses.
  • Call both constructors — Inside __init__, explicitly call each parent's constructor to set up all attributes from both parents.
  • Accesses both — The child can call methods from either parent class.
  • Use case — A consultancy employee who needs both internal company data (from Company) and client company info (from ClientCompany).
  • Rare but powerful — Used in mix-in patterns when you need to combine unrelated features into one class.
class ClientCompany:
    def __init__(self, client_name):
        self.client_name = client_name

class Employee(Company, ClientCompany):   # two parents!
    def __init__(self, emp_name, co_name, client_name):
        Company.__init__(self, co_name)
        ClientCompany.__init__(self, client_name)
        self.employee_name = emp_name

🎭 Polymorphism

Same method name, different behaviors — the key to scalable design.

❓ What is Polymorphism?

Polymorphism means "many forms." Different classes can implement a method with the same name, each with its own unique behavior.

  • Same name, different logic — Three classes — API_Fetch, DB_Fetch, S3_Fetch — all have a method called fetch(), but each does something different inside.
  • Caller doesn't need to know — The code that calls source.fetch() doesn't care which class source is. It just calls fetch() and the right version runs automatically.
  • Easy to extend — Adding a new data source (e.g., File_Fetch) only requires creating a new class with a fetch() method. You never touch the calling code.
  • Safer than one big class — If you put api_fetch(), db_fetch(), s3_fetch() all in one class, every update risks breaking the others. Separate classes are much safer.

💡 Polymorphism in Action

class API_Fetch:
    def fetch(self):
        print("Fetching data from REST API")

class DB_Fetch:
    def fetch(self):
        print("Fetching data from Database")

class S3_Fetch:
    def fetch(self):
        print("Fetching data from S3 Bucket")

# One loop, three different behaviors — that's polymorphism!
for source in (API_Fetch(), DB_Fetch(), S3_Fetch()):
    source.fetch()
Interview Tip: Polymorphism promotes the Open/Closed Principle — your code is open for extension (add new classes) but closed for modification (existing code unchanged).

📂 OS Module

Navigating and interacting with the file system programmatically.

❓ What is the OS Module?

The os module is a built-in Python library that gives you tools to interact with the operating system's file system — no installation needed.

  • Built-in — Part of Python's standard library. Just write import os — nothing to install.
  • Cross-platform — Works the same on Windows, macOS, and Linux. os.path.join() automatically uses the correct separator (\ or /) for the OS.
  • Common tasks — Find where your script is running, list files in a folder, check if something is a file or directory, and build file paths dynamically.
  • Essential for data pipelines — Real data pipelines must discover files dynamically — you can't hard-code file names when new files arrive every day.

🔧 Key OS Functions You Must Know

import os

# Where is the process running from?
print(os.getcwd())                 # → C:\Users\alice\project

# Full path of the current script file
print(os.path.abspath(__file__))    # → C:\...\script.py

# Folder that contains the current script
print(os.path.dirname(__file__))    # → C:\...\utils

# List all entries in current directory
for entry in os.listdir():
    full = os.path.join(os.getcwd(), entry)
    print(f"{entry} → {'file' if os.path.isfile(full) else 'folder'}")

📈 Incremental Loading — Real Data Engineering Pattern

Process only new files (those created after the last pipeline run), using date-named CSV files and simple string comparison.

  • Scenario — A data/ folder receives a new CSV file every day, named with the date: 2026-04-15.csv, 2026-01-14.csv, etc.
  • Goal — Only process files newer than last_load. Skip already-processed ones to avoid duplicates.
  • Why string comparison works — ISO-8601 date format (YYYY-MM-DD) keeps dates in chronological order even as plain strings. "2026-04-15" > "2026-01-14" is True.
  • Skip sub-folders — Always check os.path.isfile() first so you don't accidentally try to process a folder as a CSV.
import os
data_dir  = os.path.join(os.getcwd(), 'data')
last_load = "2026-01-14"

for filename in os.listdir(data_dir):
    full_path = os.path.join(data_dir, filename)
    if not os.path.isfile(full_path):
        continue                           # skip sub-folders
    date_part = filename.split('.csv')[0]  # e.g. '2026-04-15'
    if date_part > last_load:
        print(f"✅ Processing: {filename}")
    else:
        print(f"⏭ Already done: {filename}")

🧵 Multithreading

Running multiple tasks at the same time to speed up I/O-heavy work.

❓ What is Multithreading?

Multithreading runs multiple threads (lightweight units of execution) at the same time inside a single process, allowing I/O-bound tasks to run in parallel.

  • Best for I/O-bound tasks — Tasks that spend most of their time waiting (API calls, file reads, DB queries). Threads can wait in parallel instead of one after another.
  • Not for CPU-heavy work — Python's GIL (Global Interpreter Lock) prevents true parallel CPU execution inside threads. For heavy math, use multiprocessing instead.
  • Dramatic speedup — 5 API calls × 5 seconds each = 25 seconds sequential. With threads = only ~5 seconds total (all calls run at the same time).
  • Modern tool — Use ThreadPoolExecutor from concurrent.futures, not the older threading.Thread directly. It's simpler, safer, and production-ready.

🐌 Problem: Sequential Is Slow

import time

def fetch_data(url):
    time.sleep(5)    # simulate 5-sec API call
    return f"Data from {url}"

urls = ["url1", "url2", "url3", "url4", "url5"]
for u in urls:
    print(fetch_data(u))
# Total time: 5 × 5 = 25 seconds 😴

⚡ Solution: ThreadPoolExecutor

ThreadPoolExecutor manages a pool of threads, runs tasks in parallel, and collects results — all with minimal code.

  • max_workers — How many threads to run simultaneously. For small lists, set it to len(urls). For large lists, cap it at 100–200 to avoid overwhelming system resources.
  • executor.map(fn, list) — Submits all tasks and returns results in the same order as inputs. Best for uniform tasks with no special per-task control needed.
  • executor.submit(fn, *args) — Returns a Future object per task. Use when you need per-task control like checking errors, cancellation, or timeout.
  • Context manager — Using with ThreadPoolExecutor(...) as executor: automatically shuts down the pool and waits for all threads when done.
from concurrent.futures import ThreadPoolExecutor
import time

def fetch_data(url):
    time.sleep(5)
    return f"Data from {url}"

urls = ["url1", "url2", "url3", "url4", "url5"]

with ThreadPoolExecutor(max_workers=len(urls)) as executor:
    results = list(executor.map(fetch_data, urls))

print(results)
# Total time: ~5 seconds ✅ (all 5 run in parallel!)

Chapter 7

⚡ Asynchronous Programming (asyncio)

Handling many I/O tasks at once with a single thread using cooperative scheduling.

❓ What is Async Programming?

Async programming lets a single thread handle many I/O tasks at the same time by voluntarily "pausing" when waiting and letting other tasks run during that wait.

  • Cooperative multitasking — Unlike threads, async tasks voluntarily give up control when they hit an await. The event loop then picks the next ready task.
  • Single thread — No extra OS threads are created. Everything runs on one thread, which means lower memory and overhead compared to multithreading.
  • Event loop — The engine that manages all coroutines. It constantly checks which coroutines are ready to continue and switches between them instantly.
  • Best for — High-concurrency I/O: fetching from many APIs, reading many files, or querying many databases at once.

🔑 Key Keywords: async def, await, asyncio.run()

  • async def — Declares a function as a coroutine. It cannot be called like a normal function — it must be awaited or run via asyncio.run().
  • await — Pauses the current coroutine and gives control back to the event loop so other coroutines can run. Without await, the coroutine blocks the thread just like regular code.
  • asyncio.sleep(n) — The async-friendly version of time.sleep(). It pauses the coroutine without blocking the thread. Always use this inside async def functions — never use time.sleep() in async code.
  • asyncio.run(coro) — The entry point. Creates the event loop and runs your top-level coroutine. Call this from regular (synchronous) code to kick off everything.
import asyncio

async def main():
    print("hello")
    await asyncio.sleep(3)   # thread is FREE during these 3 seconds
    print("world")

asyncio.run(main())
Common Mistake: Never use time.sleep() inside an async def function — it blocks the entire thread and completely defeats the purpose of async. Always use await asyncio.sleep().

🔄 Running Many Coroutines Together: asyncio.gather()

asyncio.gather() runs multiple coroutines concurrently and returns all their results together, in the same order as the inputs.

  • Pass with * — Unpack your list of coroutines: await asyncio.gather(*tasks).
  • Concurrent execution — All coroutines start at nearly the same time. Total runtime = the longest single task, not the sum of all.
  • Ordered results — Results come back in the same order as your input list, even if tasks finish at different times.
  • The "All-Async" rule — Any function called with await must itself be declared as async def. Awaiting a regular function raises a RuntimeWarning.
import asyncio

async def api_call(name, delay):
    await asyncio.sleep(delay)
    return f"{name} data fetched"

async def main():
    tasks = [
        api_call("orders",    3),
        api_call("customers", 2),
        api_call("products",  1),
    ]
    results = await asyncio.gather(*tasks)
    print(results)
    # Total: ~3 seconds (not 3+2+1=6) ✅

asyncio.run(main())

🌐 API Calls, HTTP, and Authentication

How to communicate with external services using Python's requests library.

❓ What is an API?

An API (Application Programming Interface) is a secure middleman between your Python script and a backend database or service.

  • Why APIs exist — You almost never get direct database access in production. The API acts as the secure, controlled gateway.
  • Endpoints — An API exposes specific URLs (endpoints) for each resource, e.g., /orders, /customers, /products.
  • Public endpoints — No login required. Anyone can call them and get data back.
  • Private endpoints — Require authentication, typically a JWT (JSON Web Token) passed in the request header.
  • Flow — Your code → API → Database → API → Your code. The API handles validation and access control in between.

🐍 Making API Calls with requests

The requests library is Python's standard tool for making HTTP calls. Install once with pip install requests.

  • response.status_code — The HTTP status code (200 = success, 404 = not found, etc.). Always check this first.
  • response.json() — Parses the response body as JSON and returns a Python dict or list. The most common way to read API responses.
  • response.text — Returns the raw response body as a plain string.
  • GET uses requests.get(url). POST uses requests.post(url, json=data) where json= automatically sets the Content-Type header.
import requests, json

# GET — retrieve data
response = requests.get("https://jsonplaceholder.typicode.com/posts/1")
print(response.status_code)    # → 200
print(response.json())         # → Python dict

# POST — create data
data     = {"title": "My Post", "body": "Content", "userId": 1}
response = requests.post("https://jsonplaceholder.typicode.com/posts", json=data)
print(response.status_code)    # → 201 Created

🔑 Query Parameters and Authentication Headers

  • Query parameters — Key-value pairs appended to a URL after ? (e.g., ?userId=1&id=5). Pass them as a dict to params= and requests builds the URL for you.
  • JWT Auth — Send the token in the Authorization header as Bearer <token>. Required for private/protected endpoints.
  • API Key Auth — Send via X-API-Key header. Common for AI/LLM APIs like OpenAI.
  • Basic Auth — Use auth=HTTPBasicAuth("user", "pass"). requests automatically base-64 encodes the credentials.
# Query parameters — requests builds the URL automatically
response = requests.get(url, params={"userId": 1, "id": 5})

# JWT Bearer token
headers  = {"Authorization": f"Bearer {jwt_token}",
             "Content-Type":  "application/json"}
response = requests.get(secure_url, headers=headers)

# API Key authentication
response = requests.get(ai_url, headers={"X-API-Key": api_key})

🛡️ Pydantic — Schema Validation

Enforcing strict data types and rules at the point of data entry.

❓ What is Pydantic?

Pydantic is a Python library that validates data against a defined schema using type hints. If the data doesn't match, it raises a clear ValidationError immediately.

  • Built on type hints — You declare a class that extends BaseModel and annotate fields with types. Pydantic handles all validation automatically.
  • Fast — Partly written in Cython (compiled C). It's very performant and widely used at scale.
  • Used by FastAPI — FastAPI uses Pydantic for request/response validation, making it the industry standard for API data validation.
  • Two modes — Lenient mode (default): auto-converts compatible types (e.g., "5" → 5). Strict mode: rejects anything that isn't the exact right type — no coercion at all.
  • Clear errors — When validation fails, Pydantic tells you exactly which field failed and why, making debugging fast.

🧱 Basic Pydantic Model + Field Constraints

  • BaseModel — Your model class must extend BaseModel. Pydantic then validates all fields on instantiation.
  • Field(...) — The three dots ... mean the field is required. Add rules like min_length, max_length, ge (≥), le (≤).
  • EmailStr — Auto-validates email format. Needs pip install email-validator to work.
  • Optional[str] — Makes the field optional. If not provided, defaults to None (or whatever default you set).
  • Literal["male", "female"] — Restricts the field to only the listed allowed values. Any other value raises a ValidationError.
  • StrictInt / StrictStr — Enables strict mode for that field. Rejects coercion — the exact type must be provided.
from pydantic import BaseModel, Field, EmailStr, StrictStr, StrictInt
from typing import Optional, Literal

class Employee(BaseModel):
    name:       StrictStr = Field(..., min_length=3, max_length=50)
    age:        StrictInt = Field(..., ge=18, le=65)
    email:      EmailStr = Field(..., description="Valid email")
    department: Optional[StrictStr] = None   # optional — defaults to None
    gender:     Literal["male", "female"] = Field(...)

# ✅ Valid — passes all rules
emp = Employee(name="Alice", age=30, email="a@b.com", gender="female")

# ❌ Invalid — age=17 is below ge=18 → ValidationError
# Employee(name="Bob", age=17, email="b@b.com", gender="male")

🔄 Serialization: Exporting Your Model Data

  • model_dump() — Converts the Pydantic model to a plain Python dictionary. You can then access, iterate, or pass it to any function that expects a dict.
  • model_dump_json() — Converts the model to a JSON string. Perfect when you need to send data to another API or store it as JSON.
  • Round-trip — You can reconstruct a model from JSON: Employee(**json.loads(emp_json)). Validation runs again on reconstruction, keeping your data clean.
emp = Employee(name="Alice", age=30, email="a@b.com", gender="female")

emp_dict = emp.model_dump()
print(emp_dict["name"])      # → Alice

emp_json = emp.model_dump_json()
print(emp_json)               # → {"name":"Alice","age":30,...}

# Reconstruct from JSON
import json
emp2 = Employee(**json.loads(emp_json))  # validation runs again

🧪 Testing with pytest

Writing automated tests to prove your code works correctly every time.

❓ What is pytest and Why Test?

pytest is Python's most popular testing framework. It lets you write functions that automatically verify your code produces the correct output for given inputs.

  • Catch bugs early — Tests fail the moment you introduce a bug, before it ever reaches production users.
  • Confidence to change code — With tests covering your code, you can refactor or add features knowing the tests will alert you if something breaks.
  • File naming convention — Test files must be named test_*.py (e.g., test_weather.py) and test functions must start with test_.
  • Run all tests — One command: pytest ./tests/. Passing tests show a green dot ., failing ones show F with a full traceback.
  • One function per scenario — Create a fresh object inside each test function. Don't share state between tests — it leads to unpredictable failures.

✍️ Writing Your First Test with assert

An assert statement checks that actual output equals expected output. If false, pytest marks the test as FAILED and shows you why.

  • Test every branch — Test the freezing case, the chilly case, the pleasant case, and the hot case. Don't just test the happy path.
  • One test function per behavior — Keeps failures easy to pinpoint. If test_freezing fails, you know exactly which scenario broke.
  • Import from your module — Use from weather import weather_check to pull in the function you're testing.
# weather.py
def weather_check(temp: int) -> str:
    if temp < 0:   return "freezing"
    if temp < 15:  return "bit chilly"
    if temp < 25:  return "pleasant"
    return "hot"

# test_weather.py
from weather import weather_check

def test_weather_check():
    assert weather_check(-5) == "freezing"
    assert weather_check(10) == "bit chilly"
    assert weather_check(20) == "pleasant"
    assert weather_check(30) == "hot"

🎯 Parameterized Testing — Test Many Cases Cleanly

@pytest.mark.parametrize runs the same test function multiple times with different inputs, keeping your tests clean and scalable.

  • Why not many asserts in one function? — It becomes cluttered fast, and when one assert fails, the rest don't run. You don't know if the other cases pass or fail.
  • How it works — Pass a string of parameter names (comma-separated) and a list of tuples (one tuple per test case). pytest runs the function once per tuple.
  • Single assert in body — The function body stays clean with just one assert statement. All variation is in the decorator's list.
  • Easy to extend — Adding a new test case is just adding one more tuple to the list — no new function needed.
import pytest
from weather import weather_check

@pytest.mark.parametrize("temp, expected", [
    (-5,  "freezing"),
    (10,  "bit chilly"),
    (20,  "pleasant"),
    (30,  "hot"),
])
def test_weather(temp, expected):
    assert weather_check(temp) == expected
# pytest runs this 4 times — once per row in the list above

💥 Testing That Errors Are Raised: pytest.raises()

Use pytest.raises() to verify your code correctly raises an exception when given invalid input.

  • Context manager — Wrap the call that should raise in a with pytest.raises(ErrorType): block.
  • Test passes if exception IS raised — If the exception fires, the test passes. If it doesn't fire, the test fails (meaning your code didn't handle the bad input correctly).
  • match= argument — Optionally check the error message contains specific text using match="expected text".
  • Why important — Ensures your error-handling logic actually works. Don't just test the happy path — test that bad inputs are rejected properly.
# divide.py
def divide(a, b):
    if b == 0:
        raise ValueError("cannot divide by 0")
    return a / b

# test_divide.py
import pytest
from divide import divide

def test_divide_by_zero():
    with pytest.raises(ValueError, match="cannot divide by 0"):
        divide(3, 0)   # ← must raise ValueError → test passes ✅

🎭 Mocking External API Calls

Mocking replaces a real external dependency (like an API call) with a fake stand-in so tests are fast, reliable, and don't need network access.

  • Why mock? — You don't want tests to fail because an external server is down, slow, or returns different data each time. Tests must be deterministic and fast.
  • Install — pip install pytest-mock. Then use the mocker fixture which is automatically injected into test functions.
  • mocker.patch() — Intercepts the specified function call and replaces it with a fake that returns whatever you define. The real network call never happens.
  • Target path — Patch the function where it's used, not where it's defined. So if mymodule.py imports requests, patch "mymodule.requests.get".
  • Test only your logic — With the API mocked, you're testing only your function's logic — not the behavior of the external server.
# mymodule.py
import requests
def fetch_weather(url):
    return requests.get(url).json()

# test_mymodule.py
from mymodule import fetch_weather

def test_fetch_weather(mocker):
    mock_data = {"weather": "sunny"}
    mocker.patch(
        "mymodule.requests.get",
        return_value=type("R", (), {"json": lambda s: mock_data})()
    )
    result = fetch_weather("https://api.example.com/weather")
    assert result == mock_data   # ✅ no real network call made!
